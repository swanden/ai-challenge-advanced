# День 9. Декомпозиция инференса (multi-stage inference)

## Условие задания

> 🔥 День 9. Декомпозиция инференса (multi-stage inference)
>
> Возьмите задачу, которая плохо решается одним запросом:
> 👉 сложная классификация
> 👉 извлечение нескольких полей
> 👉 принятие решения на основе условий
>
> Реализуйте декомпозицию инференса:
> 👉 Вариант A: monolithic — один большой запрос, один ответ
> 👉 Вариант B: multi-stage — этап 1: анализ / нормализация входа; этап 2: принятие
> решения / классификация; этап 3: формирование результата
>
> Важно:
> 👉 каждый этап — короткий и дешёвый запрос
> 👉 можно использовать разные модели
> 👉 формат каждого этапа — строгий (enum / TOON / compact)
>
> Формат: Видео + Код

## Краткое содержание

Раздел для того, чтобы понять суть, не читая остального.

### Что просили сделать

Есть два способа заставить языковую модель решить сложную задачу. Можно задать один
большой вопрос и получить один ответ — это монолитный подход. Можно разбить задачу на
несколько коротких шагов, где каждый следующий опирается на результат предыдущего.
Задание требовало реализовать оба и сравнить: действительно ли разбивка работает лучше.

### На какой задаче проверяли

С шестого дня в проекте живёт классификатор. Он читает формулировку задачи разработчика
и определяет, к какому из восьми типов она относится:

| класс | что означает |
|---|---|
| `bug-fix` | поведение расходится с описанным, надо найти причину и починить |
| `feature` | новая функциональность поверх существующей, старое не ломается |
| `refactor` | внутренняя перестройка, снаружи ничего не меняется |
| `testing` | продукт работы — проверки: тесты, прогоны, сценарии |
| `docs` | привести документацию в соответствие коду |
| `research` | вопрос об устройстве кода, репозиторий не меняется |
| `review` | оценить готовый код или диф |
| `contract-change` | выполнение изменит договорённости, на которые опираются другие |

Последний тип особенный. Он означает, что задача незаметно поменяет то, на что
рассчитывают внешние потребители сервиса — форму ответа, код статуса, имя метода, — и
потому её нельзя отдавать программе-помощнику без присмотра человека. Понятие это
существует только внутри нашего проекта, ни одна модель не знает его из общих
соображений, и три предыдущих дня показали, что именно этот класс модель проваливает
неизменно.

Данные для обучения и замеров лежат в формате, где каждая строка — отдельный диалог из
трёх реплик: указание модели, формулировка задачи, эталонный ответ.

```json
{"messages":[{"role":"system","content":"Ты маршрутизатор задач репозитория notes-api…"},{"role":"user","content":"Сервер не дожидается активных запросов при остановке, graceful shutdown завершает процесс сразу"},{"role":"assistant","content":"bug-fix"}]}
{"messages":[{"role":"system","content":"Ты маршрутизатор задач репозитория notes-api…"},{"role":"user","content":"Отдавать на создание заметки 201 и заголовок Location вместо нынешнего 200"},{"role":"assistant","content":"contract-change"}]}
```

Вторая строка — как раз тот случай, который модель не распознаёт: формулировка выглядит
как обычная доработка, а на деле сломает существующего клиента.

### Что сделали

Разбили один вопрос на три шага: разбор формулировки на признаки, решение, сборка
ответа. Ключевое было во втором шаге. Вместо того чтобы просить модель выбрать один
вариант из восьми, ей сначала задавали отдельный вопрос с ответом «да» или «нет» —
затронет ли задача те самые договорённости. И только при отрицательном ответе выбирали
тип из оставшихся семи.

Выглядит это так. Для формулировки «переименовать в JSON-ответе поле text в body,
фронтенд уже ждёт body» разбивка даёт:

```
шаг 1  →  visible=yes; artifact=no; mode=order; product=code
шаг 2а →  «станет ли внешнее поведение другим?» → yes
шаг 2б →  не выполняется: ответ уже определён
шаг 3  →  contract-change
```

А для формулировки «в storage/memory.go мьютекс берётся и на чтение, и на запись,
переведи на RWMutex, поведение прежнее»:

```
шаг 1  →  visible=no; artifact=no; mode=order; product=code
шаг 2а →  «станет ли внешнее поведение другим?» → no
шаг 2б →  выбор из семи оставшихся классов → refactor
шаг 3  →  проверка: refactor и visible=no не противоречат друг другу → refactor
```

Прогнали три раза на одном наборе из тридцати двух примеров, поправив между прогонами
формулировку вопроса о договорённостях.

### Что получилось

Замысел оправдался ровно там, куда целились: проблемный класс модель стала определять
безошибочно — два случая из двух вместо нуля. Но всё остальное просело. Обычные баги
она стала определять втрое хуже, потому что вопрос про договорённости сбивал её с толку:
увидев упоминание кода ответа сервера, она отвечала «да» даже там, где чинили ошибку, а
не меняли правила. В сумме точность упала с 63 до 53 процентов, а расход вырос в шесть
раз по токенам.

Первый шаг вообще оказался бесполезным: без него результат тот же, а стоит вдвое дешевле.

### Вывод

Разбивка на этапы — не улучшение сама по себе. Она помогает, когда у ответа есть
внутреннее устройство, которое можно разложить на части: у других участников курса, где
из текста извлекали девять разных полей или применяли шесть правил подряд, декомпозиция
выиграла. У нас ответ — одно слово, разбирать в нём нечего, а единственная трудность в
том, что модели не хватает знания о конкретном проекте. Разбивка эту нехватку не
восполняет, зато ломает то, что раньше работало.

И более общее: отрицательный результат виден только потому, что рядом гоняли монолитный
вариант. Без него цифра 53 процента выглядела бы достижением — сравнивать было бы не с
чем.

## Задача, которая плохо решается одним запросом

Не пришлось выбирать: она уже измерена трижды. Классификатор из Дня 6 определяет по
формулировке, куда задача едет дальше в сборке `notes-api`, и все три предыдущих дня
показали одно и то же слабое место.

День 6: точность 56% на локальной модели, обе ошибки на классе `contract-change`.
День 7: механизм оценки уверенности эти ошибки не увидел — они прошли с вероятностью
1.00 и 0.93 при полном согласии перестановок промпта. День 8: маршрутизация подняла
точность с 63% до 68%, но весь выигрыш дал не confidence, а рукописный словарь, который
поймал один `contract-change` из двух — и промахнулся на втором, потому что не знал слова
«заголовок» и не видел кодов статусов, записанных цифрами.

То есть за три дня один и тот же класс провалили три разных механизма. Декомпозиция —
четвёртая попытка, и на этот раз лечение адресное.

## В чём идея разбивки

Монолитный запрос предлагает модели выбрать один класс из восьми. В этом выборе
`contract-change` конкурирует с семью соседями, и модель берёт ближайший знакомый:
`feature`, если задача выглядит как добавление, `refactor`, если как перестройка.

Многоэтапная схема убирает конкуренцию. Второй этап начинается с отдельного бинарного
вопроса — затрагивает ли задача публичный контракт, да или нет, — и класс выбирается
только при отрицательном ответе, причём из семи оставшихся.

Выигрыш тут двойной. Во-первых, вероятность распределяется между двумя ответами, а не
размазывается по восьми. Во-вторых, и это важнее, бинарный вопрос можно задать
содержательно: перечислить, что считается контрактом — коды статусов, заголовки, форма
тела ответа, путь маршрута, сигнатура экспортированного метода. В общем промпте так не
сделать, не подсказав заодно определения остальных семи классов, а это ровно то, чего мы
избегали с Дня 6: знание, поданное промптом, ничего не проверяет.

Устройство всех трёх этапов и записанные до прогона ожидания — в `docs/stages.md`.

## Три этапа

**Первый, нормализация.** Из формулировки извлекаются четыре признака строгого вида:
меняется ли внешне наблюдаемое поведение, есть ли готовый артефакт на оценку, спрашивают
или поручают, что является продуктом работы. Ответ — одна строка перечислений, не проза.

**Второй, решение.** Бинарный вопрос про контракт, затем при необходимости выбор класса
из семи. Признаки первого этапа передаются как подсказка, а не как готовый ответ: второй
этап вправе с ними не согласиться.

**Третий, сборка.** Модель не вызывается: проверяется, что признаки не противоречат
выбранному классу — `review` без артефакта, `docs` с продуктом-кодом, `refactor` с
изменением внешнего поведения. Это те же правила, что в таксономии Дня 6, и спрашивать их
у модели значит добавлять шум там, где ответ известен точно. Зато появляется сигнал,
которого у монолита нет в принципе: результат внутренне противоречив.

## На чём тестируется

Те же тридцать два входа, что в Днях 7 и 8: шестнадцать примеров из `eval` Дня 6 с
известными верными ответами, восемь пограничных формулировок и восемь шумных. Набор не
менялся с седьмого дня намеренно — только так цифры четырёх дней сравнимы напрямую, а не
«примерно».

Точки для сравнения уже есть: 56% в Дне 6 при `temperature=0`, 63% на малой модели в
Дне 8, 68% маршрутизация, 74% большая модель. Многоэтапная схема встаёт в этот ряд пятой.

## Команды воспроизведения

Из корня репозитория, Ollama поднята:

```sh
go build ./week-2/task-9/...
go run ./week-2/task-9/cmd/pipeline -mode all -note "монолит, три этапа, два этапа"
```

Режим `all` прогоняет три варианта: монолит, полную схему и двухэтапную — без
нормализации. Последняя появилась после первого прогона, когда выяснилось, что первый
этап ни на что не влияет.

Смешанная раскладка моделей — отдельный прогон:

```sh
ollama pull qwen2.5:3b
go run ./week-2/task-9/cmd/pipeline -mode multistage \
    -normalize-model qwen2.5:3b -note "нормализация на 3b"
```

Обе модели прогреваются до замера, иначе загрузка весов ложится на тот режим, который шёл
первым. Отключается флагом `-warmup=false`.

## Результаты

Прогонов было три, и каждый следующий отвечал на вопрос, поставленный предыдущим.
Все на одних и тех же тридцати двух входах, модель `qwen2.5:7b`, обе модели прогреты до
замера. Отчёты в `evidence/`.

| вариант | точность | вызовов | токенов промпта | задержка/вход |
|---|---|---|---|---|
| монолит | **63%** | 32 | 3 364 | 210 мс |
| три этапа, первая версия вопроса | 47% | 93 | 20 592 | 814 мс |
| два этапа, первая версия вопроса | 47% | 56 | 10 696 | 353 мс |
| три этапа, исправленный вопрос | 53% | 94 | 27 354 | 829 мс |
| два этапа, исправленный вопрос | 53% | 60 | 17 774 | 383 мс |

Монолит выиграл у всех вариантов декомпозиции. Это отрицательный результат, и ниже —
как он получился и почему он не случаен.

### Главная гипотеза подтвердилась

Ради чего всё затевалось: `contract-change` был 0 из 2 у монолита во всех прогонах Дней
6–9. Отдельный бинарный вопрос даёт 2 из 2 в двухэтапной схеме, устойчиво, во всех трёх
прогонах.

То есть замысел верен. Класс, который три предыдущих механизма провалили — обычная
классификация, оценка уверенности, маршрутизация по словарю, — решается адресным
вопросом полностью.

### И этого оказалось недостаточно

Выигрыш на одном классе обошёлся дороже, чем принёс. По классам, двухэтапная схема
против монолита:

| класс | монолит | два этапа |
|---|---|---|
| contract-change | 0/2 | **2/2** |
| bug-fix | **5/5** | 2/5 |
| feature | **1/2** | 0/2 |
| refactor | 1/2 | **2/2** |
| testing | **2/2** | 1/2 |
| docs | 2/2 | 2/2 |
| research | 1/2 | 1/2 |
| review | 0/2 | 0/2 |

Два приобретённых ответа против четырёх потерянных.

### Первая причина: вопрос научился видеть контракт всюду

В первой версии промпт вопроса перечислял, что относится к контракту — коды статусов,
заголовки, форма тела ответа, пути маршрутов. Модель выучила эти слова и стала отвечать
утвердительно везде, где они встречаются: восемь «да» на тридцать два входа, из них
верных два.

Пример, объясняющий всё: `eval-01` — «хендлер удаления отвечает StatusOK вместо
StatusNoContent, хотя в описании API стоит 204». Здесь описание не меняется, чинят код,
который ему не соответствует. Это `bug-fix`, и в таксономии Дня 6 различие записано
явно. Модель ответила «да», потому что увидела код статуса.

Промпт был переписан: вопрос задан через само различие — станет ли поведение **другим**
по сравнению с описанным, или задача приводит поведение **к** описанному, — с четырьмя
примерами на каждый ответ.

Помогло наполовину. Ложных «да» стало вдвое меньше, `eval-15` и `noisy-07` вернулись в
свои классы. Но `eval-01` остался ложным «да» — притом что этот самый случай вписан в
промпт почти дословно, отдельным примером. Модель не удержала различие даже так.

### Вторая причина, и она важнее: сужение списка сбивает выбор

После исправления вопроса `bug-fix` поднялся с 1 из 5 всего до 2 из 5, а не до пяти.
Значит ложные «да» были не единственной бедой.

Три бага теряются уже на втором вызове, там, где `contract-change` из списка убран и
модель выбирает из семи оставшихся. `eval-13` и `eval-14` уходят не туда, `eval-08` в
`refactor`. Похоже, фраза «уже установлено, что контракт не меняется» вместе с укороченным
списком подталкивает модель к перестроечным классам: `refactor` в двухэтапной схеме
поднялся до 2 из 2, тогда как у монолита был 1 из 2.

Иначе говоря, второй этап не просто дорабатывает решение первого — он получает другую
задачу и решает её иначе. Не всегда лучше.

### Первый этап оказался чистым расходом

Нормализация не повлияла ни на что. Двухэтапная схема, где её нет вовсе, даёт ту же
точность при вдвое меньшем расходе токенов: 47% против 47% и 53% против 53% в обеих
версиях промпта.

Отдельный прогон подтвердил это ещё жёстче. На `qwen2.5:3b` первый этап ломался в трети
случаев — признаки не разбирались одиннадцать раз из тридцати двух против одного на
семёрке, несогласованных результатов стало двенадцать против двух, — а итоговая точность
осталась ровно той же, 47%.

Причём когда признаки не разбирались, подсказка во второй этап не передавалась, и он
работал чище: именно так `eval-04` на сломанной нормализации решился верно. Слабая модель
случайно улучшила результат тем, что перестала мешать.

### Что оказалось неверным в записанных заранее ожиданиях

**«Многоэтапная схема поднимет точность на `contract-change`»** — верно, и это
единственное, что сбылось полностью.

**«Появятся ложные да»** — верно, и масштаб недооценён: восемь из тридцати двух в первой
версии.

**«Стоимость вырастет втрое»** — верно по вызовам, занижено по токенам промпта: рост в
шесть-восемь раз, потому что промпты этапов длиннее общего. Любопытно, что у dpmn на
аналогичном замере токены промпта выросли всего в 1.8 раза при десятикратном числе
вызовов — его этапы действительно короткие, наши нет.

**«Ошибки этапов будут складываться»** — не подтвердилось, потому что первый этап вообще
ни на что не влиял.

**«Смешанная раскладка окажется хуже базовой»** — не подтвердилось: те же 47% при вдвое
худшем разборе признаков. Это не «раскладка не хуже», а «первый этап не нужен».

Отдельно про мою же гипотезу, высказанную между вторым и третьим прогоном: я предсказал,
что двухэтапная схема без подсказок даст около 63%. Вышло 47%. Значит вредили не подсказки
нормализации, а сам вопрос — и это выяснилось только замером.

### Про честность последнего прогона

Промпт вопроса правился после того, как я увидел ошибки на конкретных входах, и примеры
в нём написаны по мотивам `eval-01` и `eval-03`. Проверка на этом же наборе после такой
правки перестаёт быть независимой: цифра 53% получена на данных, под которые промпт
подгонялся.

Дальше я остановился сознательно. Следующая итерация была бы подгонкой в чистом виде.
Честная проверка потребовала бы другого набора — например `train.jsonl` Дня 6, который в
замерах ни разу не участвовал, — но это уже отдельный эксперимент, а не задание дня.

## Что получилось у других участников

В этот раз удалось посмотреть чужой код по-настоящему: репозитории клонированы локально,
а не прочитаны по обрывкам. Два решения оказались особенно полезными, и оба —
с противоположным нашему результатом.

### dpmn: извлечение девяти полей, `qwen3:0.6b`

Задача — вытащить из описания товара девять полей: категория, бренд, линейка, объём,
количество в упаковке, форма, назначение, оттенок, признак набора. Монолит даёт 56.1%
пополевой точности, декомпозиция с десятью вызовами — 63.3%, то есть плюс 7.2 пункта
ценой десятикратного числа вызовов и восьмикратного времени.

Ценнее самой цифры два его контрольных замера, которых больше нет ни у кого.

**Контроль на «просто больше вызовов».** Он прогнал монолит четыре раза и взял
большинство по полям — те же лишние вызовы, но без этапов. Прирост 0.8 пункта, в пределах
шума. Значит выигрыш даёт именно разбиение задачи, а не количество обращений к модели.
Попутно это третий его день подряд, когда самосогласованность на маленькой модели не
окупается, — ровно то, что мы измерили в Дне 7.

**Разрез по уровням входа.** Весь выигрыш декомпозиции пришёлся на чистые входы, плюс
15.5 пункта; на пограничных и шумных его нет вовсе. Его формулировка: разбиение помогает
модели, которая путается в структуре ответа, и не помогает той, которая не понимает вход.

И главный его вывод, попадающий прямо в наш случай: **декомпозировать стоит извлечение, а
не классификацию**. Извлечение выигрывает от адресного вопроса — `pack_count` вырос на
сорок пунктов, — а классификация по большому закрытому словарю проигрывает. Причину он
называет неожиданную и убедительную: JSON-схема с девятью ключами задаёт модели рамку, а
одиночный вопрос с перечислением вариантов — нет, и на голом перечислении маленькая модель
выдумывает несуществующие значения чаще, чем внутри структуры.

Есть у него и предупреждение против половинчатых решений: облегчённая версия на трёх
вызовах вместо десяти дала прирост в пределах шума, потому что потеряла якорь формата
монолита и не получила адресности полного разбиения. Дробить надо до конца или никак.

### Кирилл Ткачёв: решение по претензии, `deepseek-v4-flash`

Задача — по тексту претензии выбрать одно из четырёх решений: автовозврат, ручная
проверка, отказ. Шестнадцать кейсов. Монолит 14 из 16, конвейер из трёх этапов 16 из 16,
стоимость выше в полтора раза по токенам и латентности.

Обе ошибки монолита — на инъекциях: «служебная пометка» и фальшивая «первая линия»
заставили его выдать автовозврат вместо ручной проверки при суммах 98 000 и 25 000.
Конвейер устоял на обеих. Это то, чего наш День 7 не смог: там инъекция прошла через все
четыре слоя контроля с максимальной уверенностью.

Приём, которого нет ни у кого и который стоит утащить: решение второго этапа сверяется с
детерминированной функцией на коде. Модель решает, код проверяет — расхождений ноль из
шестнадцати, тогда как у монолита его собственное финальное решение разошлось с его же
извлечёнными полями дважды. Он формулирует это как проверяемость границы между этапами:
у монолита промежуточных шагов не видно, и проверить можно только пост-фактум.

Он же реализовал идею микса моделей буквально: `pro` только на первом этапе, где разбор
зашумлённого текста, а на механических этапах `flash`, с замечанием, что монолиту такой
точечный апгрейд недоступен — платить за дорогую модель пришлось бы за весь промпт
целиком.

### Почему у них вышло, а у нас нет

Разница объясняется, а не списывается на реализацию.

У обоих задача такова, что разбивка снимает нагрузку со **структуры ответа**: у dpmn
девять полей в одном JSON, у Ткачёва шесть правил и четыре решения. Каждый этап отвечает
за свой кусок, и куски не конкурируют между собой.

У нас выбор одного класса из восьми. Структуры, которую можно упростить, попросту нет —
ответ и так одно слово. Разбивка не облегчает задачу, а меняет её: второй этап получает
укороченный список и утверждение, что контракт не меняется, и решает уже другую задачу.

Вывод dpmn — декомпозировать извлечение, а не классификацию — описывает наш результат
точнее, чем мы сами сформулировали до прогона. У него это следствие пополевого разбора, у
нас — падение с 63% до 53%.

## Выводы

**Адресный вопрос лечит адресную проблему.** `contract-change` был провален монолитом во
всех прогонах четырёх дней и решается бинарным вопросом полностью, 2 из 2. Это устойчиво
и это главное содержательное приобретение дня.

**Но декомпозиция — не улучшение по умолчанию.** Каждый добавленный этап отнял больше, чем
принёс: первый оказался чистым расходом, второй сужением списка испортил четыре класса
ради двух исправленных. Итог хуже монолита на десять пунктов при цене выше в шесть раз по
токенам.

**Дробить стоит то, что имеет внутреннюю структуру.** Извлечение девяти полей дробится
хорошо — у dpmn плюс сорок пунктов на отдельном поле. Применение шести правил дробится
хорошо — у Ткачёва 16 из 16 против 14 из 16. Выбор одного слова из восьми дробить не на
что: у ответа нет частей, есть только одна трудность, и она в доменном знании, а не в
структуре.

**Промпт, перечисляющий признаки, учит модель искать эти признаки.** Подробное описание
того, что относится к контракту, дало восемь ложных срабатываний из тридцати двух.
Переписывание через различие вместо перечисления помогло вдвое — и всё равно не устранило
случай, вписанный в промпт дословным примером. Это ограничение промпт-инжиниринга,
измеренное, а не вычитанное.

**Отрицательный результат получен вовремя.** Три прогона и правка промпта между ними
стоили около часа. Если бы декомпозиция была принята без монолита рядом, отчёт содержал бы
цифру 53% и вывод «работает», потому что сравнивать было бы не с чем. Наличие варианта A
в задании — не формальность, а то, что превращает демонстрацию в измерение.

**Куда это ведёт.** Бинарный вопрос про контракт работает как узел, но проигрывает в связке
с остальным пайплайном. Это ровно тот случай, о котором автор курса говорил применительно
к файнтюну: усиливать нужно отдельный узел, а не схему целиком. Узел, который отвечает на
вопрос про контракт, — первый кандидат: у него один бинарный ответ, восемьдесят примеров
датасета Дня 6 дают по сорок на каждый вариант вместо десяти на класс, и именно ему не
хватает знания, которого нет ни в одной общей модели.

## Разбор понятий

Раздел собран из вопросов, которые возникали по ходу недели. Он не про наш код, а про то,
что стоит за словами в отчётах.

**logprobs.** Логарифм вероятности токена. Генерируя ответ, модель на каждом шаге строит
распределение вероятностей по всему словарю — десятки тысяч токенов, в сумме единица, —
выбирает один и идёт дальше. Обычно распределение выбрасывается; параметр `logprobs`
просит его сохранить.

Логарифм берут по двум причинам. Вероятность последовательности — произведение
вероятностей её токенов, а произведение сотни чисел меньше единицы быстро проваливается
туда, где обычная арифметика теряет точность; в логарифмах умножение превращается в
сложение. И сами числа удобнее: вероятность 0.5 это −0.69, а 1.0 — ровно ноль.

Обратно переводится возведением в экспоненту. Параметр `top_logprobs` просит вернуть ещё
и альтернативы на каждой позиции — что модель почти сказала вместо того, что сказала.
Отсюда берётся отрыв: вероятность выбранного токена минус вероятность ближайшего
конкурента.

Главное про смысл этих чисел выяснилось в Дне 7: они измеряют убеждённость, а не
правильность. Если понятия `contract-change` в весах модели просто нет, распределение
будет острым и уверенным вокруг неверного класса.

**Температура.** Число, на которое делятся логиты перед превращением в распределение.
Деление на малое разводит вероятности дальше друг от друга, на большое — сближает. При
нуле выбор жадный и ответ детерминирован; около единицы выбор случаен с весами по
вероятностям; выше единицы маловероятные токены получают шанс, и текст становится сначала
разнообразнее, потом бессвязным.

Аналогия с жаром работает, но с оговоркой: температура не меняет того, что модель думает.
Порядок предпочтений остаётся прежним, меняется лишь охота брать не первый вариант.
Именно поэтому в Дне 7 подъём температуры до 0.7 не дал расхождения ни на одном из
тридцати двух входов: где вероятность лидера 0.99, умеренная встряска его не подвинет.

**Проворот списка классов.** Перестановка перечисления классов внутри системного промпта
по кругу — на 1, 3, 5 позиций — при нулевой температуре. Задача не меняется ни на букву,
поэтому ответ, держащийся на смысле, обязан остаться прежним; изменившийся ответ означает
зависимость от порядка вариантов.

Этим в Дне 7 заменили температуру, и замена сработала: расхождения появились на восьми
входах вместо нуля. Попутно вскрылось, что ответ классификатора Дня 6 действительно
частично зависит от порядка имён в промпте — то есть любая его цифра точности верна для
одного конкретного порядка.

**Эскалация.** Когда дешёвая модель ответила, но ответ вызвал сомнение, тот же вопрос
переспрашивается у модели посильнее, и её ответ считается окончательным. Смысл в
экономии: дорогая модель работает не на всех входах, а только там, где дешёвая
споткнулась. В Дне 8 это дало 68% против 63% при пяти обращениях к большой модели вместо
тридцати.

**Узлы пайплайна.** Места, где система обращается к модели. До Дня 9 узел был один — сам
классификатор; вся обвязка вокруг него (проверка входа, словарь признаков контракта,
пороги, вердикт) модель не спрашивает и состоит из обычной логики.

Декомпозиция создаёт узлы: их становится два — нормализация и решение, — и они разные по
природе. Первый разбирает формулировку, второй отвечает на вопрос про внутреннее
соглашение проекта, которого нет ни в одной модели. Это делает осмысленной фразу автора
курса про то, что усиливать файнтюном надо отдельные узлы, а не пайплайн целиком: узел с
пробелом в доменном знании и узел с обычной классификацией лечатся по-разному, и второй,
возможно, не нужно лечить вовсе.
