# День 5. Execution Loop

Минимальный вариант: трекер — текстовый файл, цикл ведёт команда `/loop`, метрики считает скрипт.

## Условие задания

> 🔥 **День 5. Execution Loop: кто дольше продержится без паузы**
>
> **Подготовьте пул задач:**
> 👉 заведите 15–20 задач в трекере (GitHub Issues / Linear / Notion / даже текстовый файл)
> 👉 микс: баги, мелкие фичи, рефакторинг, недостающие тесты, документация
> 👉 каждая задача — понятная, с чётким критерием "сделано / не сделано"
>
> **Запустите ассистента в режиме execution loop:**
> 👉 ассистент берёт задачу из трекера → выполняет → коммитит → берёт следующую
> 👉 всё автономно — вы не вмешиваетесь, не подсказываете, не правите промпт между задачами
> 👉 ассистент сам выбирает профиль (Bug Fix / Research / фича) на основе задачи
>
> **Зафиксируйте метрики:**
> 👉 сколько задач выполнено подряд без вашего вмешательства
> 👉 на какой задаче сломался и почему (не понял контекст / сгенерировал нерабочий код / зациклился)
> 👉 среднее время на задачу
> 👉 процент задач, которые прошли с первого раза
>
> **Усиление:**
> 👉 доработайте правила / профили по результатам падений и запустите loop заново
> 👉 сравните: первый прогон vs второй — насколько дольше продержался
> 👉 попробуйте тот же пул на локальной модели — сколько задач вытянет она
>
> **Результат:** пул из 15–20 задач + лог выполнения (задача → результат → время) + метрика
> "сколько подряд без паузы" в двух прогонах + сравнение облако vs локальная модель
>
> **Формат:** количество времени без пауз (в минутах)

Усиление не делается: второй прогон и локальная модель — за рамками минимального варианта.
По локальной модели вывод уже получен в Дне 4: агентный цикл она не держит, так что прогон
пула на ней заведомо оборвался бы на первой задаче.

## Экономия лимита — что сделано специально

Прогон 15 задач подряд легко упирается в сессионный лимит: у участника с аналогичным
экспериментом **одна задача на Claude Code съела половину лимита** (458 секунд, 23 хода), из-за
чего он перенёс харнесс на бесплатную модель. Здесь конструкция сознательно облегчена.

**Модель — Sonnet, не Opus.** Задачи мелкие: правка в одном-двух файлах, критерий проверяется
одной командой. Opus здесь избыточен, а разница в расходе кратная. Задание модель не диктует.

**`CLAUDE.md` урезан на две трети** — 51 строка вместо 200, 2.6 КБ вместо 7.8 КБ. Убраны длинные
примеры кода: они грузятся в каждую сессию, а агент и так видит образцы в соседних файлах, куда
теперь и отправляет ссылка. Именно на этот расход жаловались в чате курса после Дня 1.

**Профили не читаются.** В Дне 2 команда велела агенту открывать файл профиля перед каждой
задачей — три файла по сотне строк. Теперь правило по типу задачи вписано в саму команду `/loop`
одной строкой на тип.

**Артефакты Дней 2–3 убраны** из каталога: субагенты, скиллы, `.mcp.json`, smoke-сценарии,
команда `/qa`. Для этой задачи они не нужны, а Claude Code сканирует каталог `.claude/`.

**Задачи локальные.** Пул переписан так, чтобы большинство задач трогали один-два файла и путь
к нужному файлу был указан прямо в формулировке — агенту не надо искать, где что лежит.

**В команде есть прямое требование экономить ходы:** не перечитывать уже прочитанное, не
пересказывать сделанное, не дублировать код в ответ, отчёт по задаче — одна строка в журнал.

Суммарно контекст, загружаемый на сессию, — около 14 КБ на все три файла вместе.

## Устройство

**Трекер** — `notes-api/docs/tasks/pool.md`, 15 задач. Задание разрешает текстовый файл, и это
самый быстрый путь. Микс по типам: 3 бага, 3 теста, 3 фичи, 3 рефакторинга, 3 документации.
У каждой задачи критерий «сделано» сформулирован так, чтобы проверялся командой, а не на глаз,
и указан файл, который надо тронуть.

**Цикл** — команда `notes-api/.claude/commands/loop.md`. Оркестрирует главный агент: берёт
задачу, сам определяет режим работы по её типу, выполняет, прогоняет ворота, коммитит, пишет
строку в журнал, берёт следующую. Человека не спрашивает ни о чём — это прописано явно, включая
запрет на уточняющие вопросы и правило «неясность трактуется в пользу продолжения». Правила по
типам задач вписаны в саму команду, отдельные файлы профилей не читаются.

**Журнал** — `notes-api/runs/run-N/tasks.jsonl`, по строке JSON на задачу: вердикт, время,
сколько раз гонялись ворота, коммит, заметка.

**Метрики и независимая проверка** — `scripts/report.sh`. Считает streak, среднее время,
процент с первой попытки, и отдельно **переключается на каждый коммит прогона и сам гоняет
ворота**. Без этого шага метрика была бы со слов агента.

## Три подсаженных бага

Задачам типа `bug` нужны настоящие дефекты, поэтому в код внесены три — каждый компилируется
и не ловится ни `vet`, ни существующими тестами:

| Задача | Дефект | Симптом |
|---|---|---|
| T-01 | `MemoryRepo.List` возвращает `var out []note.Note` вместо `make(...)` | `GET /notes` на пустом хранилище отдаёт `null` вместо `[]` |
| T-02 | `Service.UpdateText` потерял `strings.TrimSpace` перед проверкой | `PATCH` текстом из пробелов проходит с 200 вместо 400 |
| T-03 | хендлер удаления отдаёт `StatusOK` | `DELETE` отвечает 200 вместо 204 |

Все три проверены живым запросом до прогона.

## Как запускать

Из корня репозитория. **Зафиксировать базу перед прогоном** — иначе метрика по коммитам не
сойдётся:

```bash
git add -A && git commit -m "week-1/task-5: пул задач, команда /loop, подсаженные баги"
```

Прогон. Запускать из каталога проекта, чтобы команда `/loop` была видна:

```bash
cd week-1/task-5/notes-api
claude --model sonnet
```

Внутри: `Shift+Tab` до `auto mode on` (иначе цикл встанет на первом же подтверждении), затем

```
/loop 1
```

Дальше **не вмешиваться**: не отвечать, не подсказывать, не править файлы. Засечь время старта
и финиша — это и есть сдаваемая метрика «минут без паузы».

Метрики и проверка ворот после прогона:

```bash
cd <корень репозитория>
bash week-1/task-5/scripts/report.sh 1 | tee week-1/task-5/notes-api/runs/run-1/report.md
```

## Если лимит всё равно кончится

Прогон прерывается, журнал остаётся — метрики считаются по тому, что успело записаться, и streak
до момента обрыва честно отражает результат. В отчёте это фиксируется как внешняя причина
остановки, а не как провал агента: задание спрашивает, на какой задаче агент сломался и почему,
и «упёрлись в лимит» — не то же самое, что «не понял контекст».

Продолжить с той же точки можно, запустив `/loop 1` повторно: команда читает журнал и видит,
какие задачи уже с вердиктом.

## Дефект честности: агент завысил времена

Задание требует среднее время на задачу, и здесь агент подвёл. Сумма времён из журнала —
848 секунд (14.1 минуты), а весь прогон занял 664 секунды (11.1 минуты). **Сумма частей больше
целого**, чего при последовательной работе быть не может.

Вывод однозначный: агент не измерял время по задачам, а оценивал на глаз и записывал
правдоподобные числа. Команда `/loop` велела «зафиксировать время начала», но не потребовала
делать это конкретной командой — и агент подставил оценки вместо замеров.

Поэтому в метриках выше фактическое среднее посчитано от wall-clock (664 / 15 ≈ 44 с), а не по
журналу (57 с). Разница в 30% — цена нестрогой формулировки в команде.

Чинится добавлением в команду требования брать время через `date +%s` до и после задачи и
писать в журнал разность, а не оценку. Для второго прогона это первое, что стоит поправить.

Ровно такой же класс дефекта нашёл у себя другой участник курса во втором прогоне — совпадение
показательное: агент склонен заполнять поля отчёта правдоподобными значениями, если не заставить
его их измерить.

## Два автономных решения агента

Задание запрещает вмешиваться, поэтому все развилки агент проходил сам. Два случая он честно
записал в журнал, и оба заслуживают внимания.

**T-07 (`GET /notes/count`).** Реализовал через `Service.Count`, который зовёт `repo.List` и
берёт длину, вместо добавления отдельного метода в интерфейс `Repository`. Решение спорное по
эффективности — на большом хранилище считать через выгрузку всего списка расточительно, — но для
in-memory реализации приемлемо и не расширяет контракт репозитория. Компромисс разумный, и он
его проговорил.

**T-09 (фильтр `?q=`).** Изменил сигнатуру `Service.List` на `List(ctx, query)` — то есть
**поменял существующий контракт**, обосновав это тем, что других вызывающих, кроме хендлера, не
было. Формально верно, проверил и записал. Но это ровно тот шаг, за которым в реальном проекте
нужен человек: в кодовой базе побольше «других вызывающих не нашлось» — опасное допущение.

Оба случая показывают, что автономность работает, когда критерий «сделано» сформулирован
проверяемо, а решения о контрактах агент документирует. Без записи в журнал изменение сигнатуры
`List` прошло бы незамеченным.

## Мелкий дефект инструментария

В таблице отчёта колонка «профиль» пустая. Причина на моей стороне: при облегчении команды
`/loop` из формата журнальной строки убрано поле `profile` (профили перестали читаться
отдельными файлами), а скрипт `report.sh` его по-прежнему ждёт. На метрики не влияет, но в
таблице зияет пробел.

## Выводы

**Автономный цикл на 15 задач работает.** Streak не оборвался ни разу, ворота зелёные на всех
пятнадцати коммитах по независимой проверке, вмешательств не было. Задание спрашивает, на какой
задаче агент сломался — ответ: ни на какой.

**Экономия конструкции важнее выбора модели.** Sonnet прошёл весь пул за 11 минут там, где у
другого участника одна задача на Opus съела половину лимита. Решающими оказались урезанный до
51 строки `CLAUDE.md`, отказ от чтения файлов профилей, задачи с указанным файлом и прямой запрет
на пересказ сделанного.

**Проверяемый критерий «сделано» — то, что делает автономность возможной.** Все пятнадцать задач
прошли с первой попытки именно потому, что готовность формулировалась командой, а не описанием.
Там, где формулировка была нестрогой — про фиксацию времени, — агент немедленно подставил
оценку вместо замера.

**Метрики агента надо проверять независимо.** Ворота подтвердились, а времена оказались
выдуманными. Если бы отчёт строился только со слов агента, в него ушли бы неверные цифры, причём
правдоподобные — заметить их можно было только сложив и сравнив с wall-clock.

**Усиление не делалось осознанно.** Второй прогон задание предлагает делать после разбора
падений, а падений нет. Подгонять искусственный провал под сюжет смысла нет. Локальная модель
в усиление не берётся по результату Дня 4: агентный цикл она не держит, прогон оборвался бы на
первой задаче.
