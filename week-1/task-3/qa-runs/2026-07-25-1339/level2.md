# Уровень 2 — smoke через браузер (Playwright MCP)

Базовый URL: `http://localhost:8080/`. Сценарии: `docs/smoke-scenarios.md`.
Хранилище in-memory, сервер стартовал непосредственно перед прогоном (список пуст).

Прогон S1–S5 выполнил субагент `smoke-runner`. S6 он выполнить не смог (нативный `prompt`,
тула `browser_handle_dialog` в его профиле нет) — сценарий **добит оркестратором вручную**
через тот же Playwright MCP.

## Расхождения между ожиданием и фактом

1. **Каталог скриншотов.** Playwright MCP отказывается писать за пределы своих корней:
   `File access denied … Allowed roots: …/notes-api/.playwright-mcp, …/notes-api`. Субагент
   сохранил всё в `notes-api/.playwright-mcp/`, оркестратор скопировал файлы в
   `qa-runs/2026-07-25-1339/screenshots/` (17 png + лог консоли). Чтобы артефакты падали в
   `qa-runs` сразу, корень MCP-сервера надо расширить или держать каталог прогона внутри
   `notes-api`.
2. **S6 недоступен профилю `smoke-runner`.** UI редактирования построен на нативном
   `prompt` (`internal/httpapi/web/index.html:80` — `const text = prompt('Новый текст заметки:', current)`).
   Любой браузерный прогон упирается в модальный диалог, который снимается только
   `browser_handle_dialog`, а этой тулы в профиле субагента нет; при активном модальном
   состоянии блокируются и `browser_snapshot`, и `browser_take_screenshot`.
   **Варианты починки:** добавить `mcp__playwright__browser_handle_dialog` в профиль
   `smoke-runner` (минимальная правка, сценарий сразу становится автономным) либо заменить
   `prompt` на inline-редактирование с `data-testid` (`edit-input` + `save-button`) — тогда
   сценарий проверяется чисто из снапшота.
3. **S4, статус 400 виден только косвенно.** В снапшоте страницы HTTP-статус не отражён;
   отклонение запроса подтверждено записью в консоли браузера. Это ограничение проверки
   через UI, а не дефект.
