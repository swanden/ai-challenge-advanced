# День 3. Testing

Двухуровневое тестирование `notes-api`, связанное в один автономный цикл командой `/qa`.
Прогон реальный, на Claude Code (Opus 5), Playwright MCP в headless. Полный вердикт —
зелёный, оба уровня с первого запуска.

---

## 1. Условие задания

Формулировка, как она была выдана в канале курса:

> 🔥 **День 3. Testing**
>
> **Подготовьте два уровня тестирования:**
> 👉 Уровень 1 — код: unit/integration тесты на бизнес-логику
> 👉 Уровень 2 — UI: smoke-сценарии, которые агент прогоняет сам через Playwright MCP / Claude in Mobile
>

>
> **Уровень 2. Smoke через MCP:**
> 👉 опишите 3–5 пользовательских сценариев текстом (логин → создать сущность → проверить что появилась → удалить)
> 👉 агент берёт сценарий и сам протыкивает UI: открывает страницы, кликает кнопки, заполняет формы, проверяет результат
> 👉 используйте Playwright MCP (веб) или Claude in Mobile (мобилка)

> 👉 агент пишет код-тесты → прогоняет → формирует отчёт
> 👉 агент берёт smoke-сценарии → протыкивает UI через MCP → формирует отчёт со скриншотами
> 👉 если что-то упало — агент предлагает в каком месте проблема
>
> **Усиление:**
> 👉 встройте оба уровня в flow: после PR агент прогоняет код-тесты и smoke-сценарии, собирает единый отчёт
> 👉 добавьте сценарий: "я задеплоил новую фичу — обнови smoke-сценарии и прогони всё заново"
>
> **Результат:**
> Код-тесты на 3+ модуля + 3–5 smoke-сценариев, которые агент прогоняет через MCP сам +
> отчёт со скриншотами + интеграция в flow разработки
>
> **Формат:**
> Видео + Код

## 2. Что добавлено в проект под задание

`notes-api` из Дней 1–2 — чистый JSON-API без интерфейса, поэтому Уровню 2 (протыкивание UI
через браузер) тыкать было бы нечего. Под задание к проекту добавлены:

- **Веб-интерфейс** `internal/httpapi/web/index.html` — минимальная страница: список заметок,
  форма создания, кнопка удаления у каждой. Все элементы со стабильными `data-testid` под
  селекторы Playwright. Отдаётся сервером через `embed`.
- **Удаление** `DELETE /notes/{id}` и **частичное обновление** `PATCH /notes/{id}` через все
  слои (repository → service → handler), плюс кнопки «Удалить» и «Изменить» в интерфейсе — чтобы
  smoke-сценарии «создать → проверить → удалить» и «создать → изменить» имели обе половины.
  Проект стал полным CRUD.

Это осознанно смешанный вариант: honest smoke по реальному UI через браузер **плюс** проверка
API под ним (валидацию пустого текста браузер видит как сообщение на странице, а сервер
подтверждает её ответом 400).

## 3. Архитектура решения

Три механизма Claude Code, связанные в один цикл.

**Уровень 1 — субагент `test-writer`** (`.claude/agents/test-writer.md`, инструменты
`Read, Glob, Grep, Bash, Edit, Write`). Сам замеряет покрытие, сам выбирает по критериям
важности, что покрывать (список файлов ему не дают), пишет table-driven тесты в стиле проекта
и доказывает мутациями, что они ловят регрессию. Правит только `*_test.go`, продуктовый код не
трогает.

**Уровень 2 — субагент `smoke-runner`** (`.claude/agents/smoke-runner.md`). Гоняет сценарии из
`docs/smoke-scenarios.md` через Playwright MCP по реальному UI, вывод о каждом шаге делает
только из снапшота страницы. У него намеренно нет `Bash` (не поднимает сервис), `Edit`
(не чинит код) и `browser_evaluate` (не может выдернуть результат скриптом в обход интерфейса).
Это прямое продолжение находки Дня 2: структурный запрет надёжнее текстового.

**Связка — команда `/qa`** (`.claude/commands/qa.md`). Субагент не может вызвать субагента,
поэтому оркестрирует команда главного агента. Порядок: Уровень 1 → **ворота**
(build/vet/gofmt/test — на красном Уровень 2 не запускается, тыкать UI на сломанной сборке
бессмысленно) → поднять сервис → Уровень 2 → единый отчёт. Ворота оркестратор проверяет сам,
не доверяя формулировкам профилей.

Playwright MCP подключается через `.mcp.json` (npx-вариант; для чистой машины без node —
`.mcp.docker.json.example`).

| Пункт условия | Где закрыт |

| Минимум 3 файла тестов, проходят с первого запуска | 4 файла, все зелёные с первого прогона |
| Уровень 2: 3–5 сценариев текстом | 6 сценариев в `docs/smoke-scenarios.md` |
| Агент сам протыкивает UI через Playwright MCP | субагент `smoke-runner`, 5/5 пройдено |

| Если упало — где проблема | профили дают гипотезу файл:строка |
| Усиление: встроить в flow после PR | `/qa` — готовый кирпич под пост-PR хук (см. ниже) |

## 5. Как воспроизвести

Установить Playwright MCP (один раз):

```
claude mcp add playwright npx @playwright/mcp@latest
```

Весь цикл — одной командой из каталога проекта:

```
cd week-1/task-3/notes-api
claude
> /qa
```

Уровни по отдельности:

```
# Уровень 1
claude -p 'Напиши тесты на непокрытые модули' --allowedTools "Read,Glob,Grep,Bash,Edit,Write,Task"

# Уровень 2 (сервис поднять заранее)
go run ./cmd/notes-api &
claude -p 'Прогони smoke-сценарии из docs/smoke-scenarios.md' --allowedTools "Read,Glob,Grep,Write,Task"
```

Артефакты прогона складываются в `qa-runs/<дата-время>/`.

## 6. Результат прогона

Один прогон `/qa`, Opus 5, длительность 19 мин 45 с, ноль вмешательств между запуском и
вердиктом. Артефакты — в `qa-runs/2026-07-25-1155/`.

### Уровень 1 — код-тесты

Покрытие по модулю **7.0% → 82.6%**, четыре новых файла тестов:

| пакет | было | стало |
|---|---|---|
| `internal/httpapi` | 0.0% | 100.0% |
| `internal/note` | 47.1% | 94.1% |
| `internal/storage` | 0.0% | 100.0% |
| `cmd/notes-api` | 0.0% | 0.0% (только wiring) |

Продуктовый код не изменён — оркестратор проверил `git diff` сам, в статусе только новые
`*_test.go`. Непокрытой осталась одна строка: panic-ветка `RandomID.NewID` при отказе
`crypto/rand`, недостижимая без подмены `rand.Reader` — `test-writer` честно оставил её и
пометил, а не стал накручивать процент. `cmd/notes-api` (0%) тоже оставлен как склейка без
логики.

**Мутационная проверка — 23 из 23 убиты.** Это ключевой результат: для каждого нетривиального
теста агент временно ломал проверяемое место в продуктовом коде, убеждался, что тест краснеет,
и откатывал правку. Среди убитых мутаций — снятие блокировки в `MemoryRepo.Create`, которое
ловится **только под `-race`**: агент добавил `-race` в ворота сам, сверх задания, и написал
конкурентный тест под него. Это доказанная фактом разница между «покрытие выросло» и «тесты
ловят регрессии».

Одна деталь честности: первая версия `TestHandlerRouting` мутацию маршрута не ловила — агент
это заметил при проверке и усилил тест.

## 7. Что вскрылось прогоном и как обработано

Прогон дал три находки. Все три после прогона обработаны — это и есть ответ на пункт задания
«если что-то упало — агент предлагает в каком месте проблема»: цикл нашёл, отчёт назвал место,
дальше внесены правки.

**Рассинхрон `CLAUDE.md` и кода — главная находка, устранена реализацией.** Файл правил приводил
`PATCH /notes/{id}` как пример, `MemoryRepo.Update` был реализован, но ни `Service`, ни `Handler`
метода обновления не имели — реально `PATCH` отдавал 405. Это отголосок Дня 1: в той генерации
PATCH писался, но в базовую версию проекта не попал, а пример в правилах остался. `test-writer`
не стал молча чинить (не его роль) — зафиксировал поведение тестом и вынес в отчёт. **По итогам
дореализован:** добавлены `Service.UpdateText` и хендлер `PATCH` по образцу проекта, плюс кнопка
«Изменить» в интерфейсе и smoke-сценарий S6. Проверено вживую: 200 с обновлённым `updated_at`,
400 на пустой текст, 404 на несуществующий id. Проект стал полным CRUD, документация и код снова
согласованы.

**Сценарий S2 неточен — переформулирован.** Ожидание «ровно три элемента» не выполнилось: в
списке оказалось четыре, заметка из S1 пережила переход между сценариями (in-memory хранилище не
сбрасывается). Дефекта приложения нет — проверяемое поведение подтверждено. Формулировка
исправлена на «появились три новых элемента в порядке создания» с явной оговоркой про накопление
состояния.

**`favicon.ico` → 404 — устранено.** Добавлен `<link rel="icon" href="data:,">` в `index.html`,
браузер больше не запрашивает иконку, консоль чистая.

Показательно, что все три находки — разного рода: одна вскрыла реальное расхождение кода и
документации, вторая — неточность самих сценариев, третья — косметика. Цикл отработал как
предполагалось: нашёл, назвал место, дал возможность починить.

## 8. Усиление

Команда `/qa` и есть готовый кирпич под пост-PR хук: тот же цикл (код-тесты → ворота → smoke →
единый отчёт), который вешается на событие после PR и гоняется автоматически. Сценарий
«задеплоил фичу — обнови smoke и прогони заново» сводится к правке `docs/smoke-scenarios.md` и
повторному `/qa` — состояние между прогонами не накапливается, потому что сервис поднимается
заново.

## 10. Контекст: лекция и чат курса

### Из вводной лекции потока

Отдельной лекции под День 3 нет — вводная лекция потока общая и разбирает весь стек абстракций
код-агента (главный агент как оркестратор, субагенты, скиллы, команды, MCP), а не тестирование
конкретно. Тестирование в ней упоминается лишь вскользь. Поэтому методику Дня 3 задают текст
задания и практика однокурсников, а не лекция. Главная мысль лекции, применимая здесь:
главный агент не делает тяжёлую работу сам, а распределяет её между исполнителями — что мы и
реализовали, отдав уровни субагентам, а связку — команде.

### Из обсуждения в чате

Задание допускает и не-MCP путь для Уровня 2. Никита Семиклит спросил, обязательно ли через
MCP, и предложил Android CLI; автор курса ответил встречным «а как ты хочешь?» и попросил не
ограничиваться только Android, а покрыть и веб. То есть MCP — рекомендованный, но не
единственный путь; веб-часть через Playwright MCP при этом ожидается. Наш смешанный вариант
(веб-UI через Playwright MCP + проверка API под ним) этому соответствует.

Отдельная ветка чата в эти же дни — про разницу между командой и скиллом, потому что оба
вызываются через `/` и путаются. Разбор этого — в разделе 11 ниже, он прямо отвечает на
вопрос, который в чате задавали.

Ещё один сквозной мотив чата этой недели — упор в лимиты после Дня 1, потому что конфиги с
примерами кода добавляют тысячи токенов к каждому запросу. Это аргумент за то, чтобы тяжёлые
процедуры и большие инструкции держать в скиллах и субагентах (свой контекст, подгрузка по
требованию), а не в постоянно загруженном `CLAUDE.md` — что в этом задании и сделано.

## 11. Использованные абстракции Claude Code: что это и почему здесь

День 3 — первый, где задействован почти весь стек механизмов Claude Code сразу. Ниже — что
такое каждый и почему он взят именно под эту задачу.

### Команда (`/qa`) — `.claude/commands/qa.md`

**Что это.** Команда — это сохранённый шаблон промпта, вызываемый как `/имя`. По сути обычный
markdown-файл с инструкцией: когда ты набираешь `/qa`, его содержимое подставляется в диалог
как твой запрос, и главный агент начинает его выполнять. Аргументы подставляются через
`$ARGUMENTS`. Автор курса в чате сформулировал так: команда — это шорткат для промпта.

**Зачем нужна и почему здесь именно она.** Ключевое техническое ограничение: **субагент не
может вызвать другого субагента**. А Уровень 1 (`test-writer`) и Уровень 2 (`smoke-runner`) —
это два субагента, между которыми нужен третий участник: тот, кто запустит первого, проверит
ворота, поднимет сервис, запустит второго и склеит отчёт. Этим участником не может быть ни
один из субагентов. Поэтому оркестрацию держит команда — она выполняется главным агентом,
который субагентов вызывать умеет. Команда здесь — не украшение, а единственное место, где
может жить связка двух уровней в один автономный цикл, которого требует задание.

### Субагенты (`test-writer`, `smoke-runner`) — `.claude/agents/*.md`

**Что это.** Субагент — специализированный экземпляр агента с собственным окном контекста и
собственным списком разрешённых инструментов (поле `tools` в шапке файла). Главный агент
делегирует ему подзадачу через тул `Task`; субагент отрабатывает в своём контексте и возвращает
результат, не засоряя основной диалог.

**Зачем нужны и почему здесь.** Две причины. Первая — гигиена контекста: написание тестов и
прогон браузера — многошаговая работа с десятками вызовов инструментов, и держать её в основном
диалоге значит забить его контекст; субагент делает это в отдельном окне. Вторая, важнее, —
ограничение инструментов как структурный запрет: у `smoke-runner` намеренно нет `Bash`, `Edit`
и `browser_evaluate`, поэтому он физически не может ни починить код по ходу, ни выдернуть
результат скриптом в обход интерфейса. Задание требует, чтобы smoke проверял то, что видит
пользователь; на субагенте это гарантируется набором инструментов, а не обещанием в промпте.
Это прямое продолжение вывода Дня 2.

### Скиллы — упоминание

**Что это.** Скилл — процедура в `.claude/skills/<имя>/SKILL.md`, подгружаемая по необходимости,
когда её описание совпадает с задачей, а не висящая в контексте постоянно.

**Почему здесь их нет как отдельных файлов.** В Дне 2 скиллы уже были заведены (`http-repro`,
`regression-test`) и относятся к профилю bug-fix. В Дне 3 их роль поглощена субагентами:
`test-writer` несёт процедуру мутационной проверки прямо в своей инструкции, потому что она
неотделима от его единственной задачи. Выносить её в отдельный скилл имело бы смысл, если бы её
переиспользовали несколько разных агентов — здесь потребитель один, и отдельный файл только
добавил бы косвенности.

### MCP-сервер (Playwright) — `.mcp.json`

**Что это.** MCP (Model Context Protocol) — стандарт, которым Claude Code подключает внешние
инструменты. Playwright MCP — сервер, дающий агенту тулы управления реальным браузером
(`browser_navigate`, `browser_click`, `browser_snapshot`, `browser_take_screenshot` и другие).
Ключевая деталь: сервер по умолчанию возвращает не скриншот, а дерево доступности страницы —
структурированный текст с ролями и именами элементов, поэтому агент действует по семантике, как
пользователь, а не по координатам пикселей.

**Зачем нужен и почему здесь.** Это буквально инструмент, названный в задании для Уровня 2: без
него агенту нечем «протыкивать UI». Именно MCP превращает smoke-сценарий из текста в реальные
клики по живой странице, а дерево доступности даёт стабильные проверки (появился элемент с таким
текстом), не зависящие от вёрстки.

### CLAUDE.md — правила проекта

**Что это.** Markdown-файл, который Claude Code читает автоматически при старте сессии и
вставляет в системный промпт. Постоянный контекст: конвенции, стек, команды.

**Зачем здесь.** Именно из него оба субагента берут стиль проекта — table-driven тесты,
подмену зависимостей дублями, сверку ошибок через `errors.Is`. Без него `test-writer` писал бы
тесты в каком-то своём стиле, а не в стиле кодовой базы. Показательно, что именно рассинхрон
`CLAUDE.md` с кодом (пример `PATCH`, которого не было в реализации) стал одной из находок
прогона — то есть правила реально сверяются с кодом, а не игнорируются.

### Разница команды и скилла (вопрос из чата)

Оба вызываются через `/`, отсюда путаница. Разграничение по назначению: **команда — шорткат для
промпта** (подставляет заготовленный текст запроса, который дальше выполняет главный агент);
**скилл — конкретный навык/процедура** с метаданными, который подгружается по описанию и может
исполняться в том числе в отдельном контексте субагента. В этом задании связка уровней — это
команда (`/qa`), потому что нужна оркестрация в контексте главного агента; а процедуры внутри
уровней (мутационная проверка, работа с браузером) живут в инструкциях субагентов.

## 12. Работа с Claude Code: заметки по ходу выполнения

Практические моменты, всплывшие при реальном прогоне — на случай повторения.

**Модель.** Прогон шёл на Opus 5 (обновилась с 4.8 между сессиями). На результат Дня 3 это не
влияет — он самостоятельный; но для сравнений между днями стоит помнить, что Дни 1–2 были на
Opus 4.8.

**Оплата: подписка против API.** В шапке периодически всплывало «API Usage Billing» вместо
«Claude Max» — это способ оплаты, не модель. Если в окружении нет `ANTHROPIC_API_KEY` (у нас
не было), причина — истёкший OAuth-логин, после которого Claude Code показывает fallback-строку.
Лечится `/login` с выбором «Claude account with subscription» (первый пункт). Проверка активного
метода — `/status`: строка Login method без строки API key означает работу по подписке.

**Долгая сессия.** OAuth-токен по подписке живёт около 8 часов и автоматически не
продлевается — отсюда частые «Login expired». Чтобы не логиниться каждый день, есть
`claude setup-token` — он выпускает подписочный токен на год (не API-ключ, деньги не списываются),
который прописывается в `CLAUDE_CODE_OAUTH_TOKEN`.

**Подтверждения действий.** Claude Code по умолчанию спрашивает разрешение перед каждым
изменяющим действием. Режим переключается на лету `Shift+Tab`: «accept edits» убирает вопросы
на правки файлов, «auto mode» — сам обрабатывает подтверждения, проверяя каждый вызов на
рискованность. Важная тонкость: **Playwright-действия (клики в браузере) не покрываются
«accept edits»** — это внешние действия, по каждому новому типу Claude Code спрашивает
отдельно; можно ответить «не спрашивать снова для этого типа» или включить auto mode.

**Каталог команд.** Кастомная команда `/qa` видна, только если Claude Code запущен из каталога,
где лежит `.claude/commands/`. Запуск на уровень выше проекта команду не подхватит — нужно
`cd` в каталог с `.claude/`.

**Длительность.** Полный `/qa` — около 20 минут (у нас 19:45), сопоставимо с аналогичными
прогонами однокурсников. Это два субагента подряд, второй с реальным браузером; нормально, что
долго.
