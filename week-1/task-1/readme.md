## 2. Площадка эксперимента

Чтобы проверка была честной, нужен был проект, который реально собирается и тестируется, иначе
критерий «прошло ли линтер» превращается в фикцию. Поэтому взят компактный, но полноценный
сервис заметок со слоёной архитектурой и без внешних зависимостей.

```
week-1/task-1/notes-api/
├── CLAUDE.md                     файл правил (по ходу эксперимента подменяется v1 <-> v2)
├── cmd/notes-api/main.go         точка входа: сборка зависимостей и graceful shutdown
└── internal/
    ├── note/                     доменный слой, ничего не знает про HTTP и хранилище
    │   ├── note.go               модель Note, Service, интерфейсы Repository/IDGenerator/Clock
    │   ├── deps.go               реализации зависимостей: RandomID и SystemClock
    │   └── note_test.go          table-driven тест сервиса на тестовых дублях
    ├── storage/memory.go         MemoryRepo — потокобезопасный Repository в памяти
    └── httpapi/handler.go        транспорт: POST /notes, GET /notes, GET /notes/{id}
```

В коде заранее заложены конвенции, которые правила потом описывают словами: `context.Context`
первым аргументом с пробросом через все слои, зависимость на интерфейсы вместо конкретных
реализаций, доменные ошибки-переменные с проверкой через `errors.Is`, время и идентификаторы
через абстракции `Clock` и `IDGenerator` ради тестируемости, структурный лог `slog`,
конструкторы `NewXxx`, table-driven тесты.

## 3. Методика

Первая версия правил написана намеренно слабой — примерно такой, какую пишут в первый заход:

Боевой промпт, дословно, без уточнений и переписок:

```
Добавь endpoint PATCH /notes/{id} для частичного обновления текста заметки. Верни обновлённую заметку.
```

Задача выбрана потому, что задевает все три слоя разом и вынуждает принять несколько

## 5. Файл правил v2 (доработанный)

````markdown
# CLAUDE.md — notes-api

Небольшой HTTP-сервис заметок на Go. Демонстрирует чистую слоёную архитектуру
на стандартной библиотеке. Этот файл описывает, как в проекте принято писать код,
чтобы новый код было не отличить от существующего.

## Стек и зависимости

Язык — Go. Код живёт в монорепозитории `github.com/swanden/ai-challenge-advanced`,
это задание — в каталоге `week-1/task-1/notes-api/`. Внутренние пакеты импортируются
полным путём модуля. Только стандартная библиотека: `net/http` для
транспорта, `log/slog` для логов, `encoding/json` для сериализации. Внешних
зависимостей нет и добавлять их без явной необходимости нельзя. HTTP-роутинг —
на `http.ServeMux` с method-шаблонами (`"PATCH /notes/{id}"`), без сторонних
роутеров.

## Архитектура (слои и направление зависимостей)

Код разбит на слои, и зависимости направлены только внутрь, к домену:

- `cmd/notes-api` — точка входа. Только сборка зависимостей (wiring), запуск
  сервера и graceful shutdown. Никакой бизнес-логики.
- `internal/note` — доменный слой. Модель `Note`, бизнес-правила в `Service`,
  интерфейсы зависимостей (`Repository`, `IDGenerator`, `Clock`). Этот пакет
  НЕ импортирует `httpapi` и `storage` и ничего не знает про HTTP и про то,
  где данные лежат физически.
- `internal/storage` — реализации `note.Repository` (сейчас `MemoryRepo`).
- `internal/httpapi` — транспорт. Разбор запроса, вызов `note.Service`,
  формирование ответа. Бизнес-логики здесь быть не должно.

Правило потока: HTTP-хендлер → `note.Service` → `note.Repository`. Хендлер
никогда не ходит в репозиторий напрямую и не реализует бизнес-правила сам.

## Naming conventions

Конструкторы называются `NewXxx` и возвращают `*Xxx` (`NewService`,
`NewMemoryRepo`, `NewHandler`). Доменные ошибки — переменные уровня пакета с
префиксом `Err` (`ErrNotFound`, `ErrEmptyText`). Экспортируются только те
идентификаторы, что нужны снаружи пакета; всё остальное — со строчной буквы.
Файлы называются по смыслу (`note.go`, `memory.go`, `handler.go`), тесты — рядом
с кодом в `_test.go`.

## Обязательные паттерны

**`context.Context` — первым аргументом каждого метода, который делает I/O или
может быть отменён.** Он прокладывается сквозь все слои: хендлер берёт
`r.Context()` и передаёт в сервис, сервис — в репозиторий. Свой контекст внутри
метода (`context.Background()`, `context.TODO()`) создавать нельзя — это обрывает
отмену и дедлайны.

**Время и идентификаторы — только через абстракции `Clock` и `IDGenerator`.**
В коде домена нельзя звать `time.Now()` или генерировать id напрямую — иначе
логику не зафиксировать в тестах. Берём `s.clock.Now()` и `s.ids.NewID()`.
Время — всегда UTC (`SystemClock.Now()` уже возвращает UTC).

**Валидация входных данных — в сервисе, а не в хендлере.** `Service` сам
делает `TrimSpace`, проверяет пустоту и возвращает доменную ошибку. Хендлер
только транслирует эту ошибку в HTTP-статус.

**Тело запроса — типизированная структура, а не `map[string]any`.** Для каждого
эндпоинта заводим `xxxRequest struct` с json-тегами. Type assertion из
`map[string]interface{}` запрещён.

**Ошибки различаем через `errors.Is` и мапим на статусы явно.** В хендлере:
`errors.Is(err, note.ErrNotFound)` → 404, `errors.Is(err, note.ErrEmptyText)`
→ 400, иначе → 500. Наружу отдаём безопасное сообщение в формате
`errorResponse{Error: ...}`, а не `err.Error()`.

**HTTP-статусы — только именованными константами** (`http.StatusNotFound`),
никогда числом.

**Ошибки не проглатываем.** Ошибку кодирования ответа логируем через `slog`
с контекстом (`h.log.ErrorContext(ctx, ...)`).

## Хороший код (эталоны из проекта)

Метод сервиса: `ctx` первым, зависимости — через абстракции, доменная ошибка
на невалидный вход.

```go
func (s *Service) Create(ctx context.Context, text string) (Note, error) {
	text = strings.TrimSpace(text)
	if text == "" {
		return Note{}, ErrEmptyText
	}
	now := s.clock.Now()
	n := Note{ID: s.ids.NewID(), Text: text, CreatedAt: now, UpdatedAt: now}
	if err := s.repo.Create(ctx, n); err != nil {
		return Note{}, err
	}
	return n, nil
}
```

Хендлер: типизированный запрос, `r.Context()` в сервис, различение ошибок,
единый формат ответа.

```go
func (h *Handler) get(w http.ResponseWriter, r *http.Request) {
	id := r.PathValue("id")
	n, err := h.svc.Get(r.Context(), id)
	if err != nil {
		if errors.Is(err, note.ErrNotFound) {
			h.writeError(w, r.Context(), http.StatusNotFound, "note not found")
			return
		}
		h.writeError(w, r.Context(), http.StatusInternalServerError, "failed to get note")
		return
	}
	h.writeJSON(w, r.Context(), http.StatusOK, n)
}
```

Метод репозитория: `ctx` первым, под блокировкой, доменная ошибка при отсутствии.

```go
func (r *MemoryRepo) Update(ctx context.Context, n note.Note) error {
	r.mu.Lock()
	defer r.mu.Unlock()
	if _, ok := r.notes[n.ID]; !ok {
		return note.ErrNotFound
	}
	r.notes[n.ID] = n
	return nil
}
```

Тест: table-driven, зависимости подменяются дублями (`fixedID`, `fixedClock`),
ошибки сверяются через `errors.Is`.

## Антипаттерны (так писать нельзя)

- Метод, делающий I/O, **без `context.Context`** первым аргументом; либо
  `context.Background()` / `context.TODO()`, созданный внутри метода.
- **`time.Now()` или генерация id напрямую** в доменном коде мимо `Clock` /
  `IDGenerator`.
- **`map[string]interface{}` для тела запроса** и `req["text"].(string)` без
  проверки `ok` — это паника на неожиданном типе.
- **Магические числа статусов** (`400`, `404`) вместо `http.StatusXxx`.
- **`http.Error(w, err.Error(), ...)`** — утечка внутренней ошибки наружу и
  потеря единого формата ответа; плюс привязка любой ошибки к одному статусу
  вместо различения через `errors.Is`.
- **Проглоченная ошибка** (`json.NewEncoder(w).Encode(v)` без проверки/лога).
- **Бизнес-логика или валидация в хендлере**; хендлер, ходящий в репозиторий
  мимо сервиса.
- Внешние зависимости и сторонние роутеры без необходимости.

## Шаблон типичного файла

```go

	// валидация → работа → возврат доменной ошибки при необходимости
````

## 8. Главная находка: сильная модель выводит стиль из кода

Вопреки ожиданию, генерация A по слабым правилам вышла почти полностью идиоматичной. Claude
Code прочитал соседние файлы и скопировал оттуда конвенции, которых в правилах v1 не было ни
словом. Совпало сразу многое: `context.Context` первым аргументом и его проброс через все слои,
обращение к абстракции `s.clock.Now()` вместо прямого `time.Now()`, валидация текста в сервисе
с доменной ошибкой `ErrEmptyText`, типизированная структура `updateRequest` вместо
`map[string]any`, различение ошибок через `errors.Is`, именованные константы `http.StatusXxx`
и единый формат ответа через собственные `writeError` и `writeJSON`.

Это ровно те пункты, которые в v2 выписаны как обязательные паттерны и антипаттерны — и модель
попала в них без правил. Вывод отсюда не в том, что правила бесполезны, а в том, что на
небольшой внутренне непротиворечивой кодовой базе они страхуют то, что иначе получается
везением.

## 9. Разница между генерациями

### 9.1. Стиль тестов — самое показательное расхождение

Правила v2 требуют, чтобы тесты были table-driven, с подменой зависимостей дублями. Генерация
B выдала именно такой тест:

```go
	tests := []struct {
		name    string
		id      string
		input   string
		wantErr error
		wantTxt string
	}{
		{name: "updates text and bumps UpdatedAt", id: "n1", input: "  new  ", wantErr: nil, wantTxt: "new"},
		{name: "empty text is rejected", id: "n1", input: "   ", wantErr: ErrEmptyText},
		{name: "missing note is not found", id: "nope", input: "x", wantErr: ErrNotFound},

			svc := NewService(repo, fixedID{id: "abc"}, fixedClock{t: updated})

			got, err := svc.Update(context.Background(), tt.id, tt.input)
			if !errors.Is(err, tt.wantErr) {
				t.Fatalf("Update() err = %v, want %v", err, tt.wantErr)
			}

				return

			}

```

Генерация A вместо этого написала три независимых подтеста с продублированной в каждом
настройкой репозитория и сервиса:

```go
	t.Run("updates text and touches UpdatedAt", func(t *testing.T) {
		repo := newFakeRepo()
		svc := NewService(repo, fixedID{id: "abc"}, fixedClock{t: updated})
		repo.notes["abc"] = Note{ID: "abc", Text: "old", CreatedAt: created, UpdatedAt: created}

		if err != nil {

	t.Run("missing note returns ErrNotFound", func(t *testing.T) {
```

Отдельно стоит подчеркнуть, почему это самое ценное наблюдение отчёта. Образец был у модели
прямо перед глазами: в том же файле `note_test.go` уже лежал table-driven `TestServiceCreate`.
Соседний код с правильным примером не удержал генерацию A от отклонения — а явное правило
удержало генерацию B. Это лучший аргумент в пользу того, что правила нужны даже там, где
кодовая база «сама всё показывает».

### 9.2. Форма разбора ошибок в хендлере

Генерация B воспроизвела структуру из примера, показанного в правилах, — последовательные
проверки с ранним возвратом:

```go
	n, err := h.svc.Update(r.Context(), r.PathValue("id"), req.Text)
	if err != nil {
		if errors.Is(err, note.ErrNotFound) {
			h.writeError(w, r.Context(), http.StatusNotFound, "note not found")
			return
		}
		if errors.Is(err, note.ErrEmptyText) {
			h.writeError(w, r.Context(), http.StatusBadRequest, "text is required")
			return
		}
		h.writeError(w, r.Context(), http.StatusInternalServerError, "failed to update note")
		return
	}
	h.writeJSON(w, r.Context(), http.StatusOK, n)
```

Генерация A изобрела собственный вариант через `switch` с веткой по умолчанию:

```go
	n, err := h.svc.Update(r.Context(), r.PathValue("id"), req.Text)
	if err != nil {
		switch {
		case errors.Is(err, note.ErrEmptyText):
			h.writeError(w, r.Context(), http.StatusBadRequest, "text is required")
		case errors.Is(err, note.ErrNotFound):
			h.writeError(w, r.Context(), http.StatusNotFound, "note not found")
		default:
			h.writeError(w, r.Context(), http.StatusInternalServerError, "failed to update note")
		}
		return
	}
	h.writeJSON(w, r.Context(), http.StatusOK, n)
```

Обе формы рабочие и обе корректно раскладывают доменные ошибки по статусам. Но единообразие с
уже существующими хендлерами `get` и `create`, где применён первый стиль, даёт только
генерация B — и ровно потому, что этот стиль был показан в правилах примером, а не описан
словами.

Всё остальное в хендлере совпало дословно, включая объявление типа запроса и разбор тела:

```go
// updateRequest — тело запроса на частичное обновление заметки.
type updateRequest struct {
	Text string `json:"text"`
}

func (h *Handler) update(w http.ResponseWriter, r *http.Request) {
	var req updateRequest
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		h.writeError(w, r.Context(), http.StatusBadRequest, "invalid json body")
		return
	}
	// ... далее расходятся, см. выше
```

Регистрация маршрута в обеих генерациях идентична:

```go
	h.mux.HandleFunc("PATCH /notes/{id}", h.update)
```

### 9.3. Детализация документирующих комментариев

Тело метода `Service.Update` в обеих генерациях совпало дословно — обе версии обрезают пробелы,
возвращают `ErrEmptyText` на пустом тексте, читают заметку через репозиторий, обновляют текст и
проставляют `UpdatedAt` из абстракции `Clock`, сохраняя `CreatedAt`. Разошлись только
комментарии.

Генерация A ограничилась перечислением возвращаемых ошибок:

```go
// Update заменяет текст существующей заметки и обновляет метку времени.
// Возвращает ErrEmptyText при пустом тексте и ErrNotFound, если заметки нет.
```

Генерация B описала поведение полнее, явно упомянув сохранение `CreatedAt`:

```go
// Update частично обновляет текст заметки: проверяет ввод, подтягивает
// существующую заметку, меняет текст и метку UpdatedAt (CreatedAt сохраняется)
// и возвращает обновлённую заметку. Нет такой заметки — ErrNotFound.
```

Это мелочь, но она прямо следует из требования правил документировать экспортируемые методы
содержательно.

## 10. Что больше всего повлияло на качество

Сильнее всего сработали **примеры кода, взятые прямо из проекта и вставленные в правила**.
Именно их форму генерация B повторила буквально — и в структуре теста, и в способе разбора
ошибок. Модель копирует показанный образец охотнее, чем следует описанию словами, поэтому один
хороший пример стоит абзаца формулировок.

На втором месте — **явные требования там, где код допускает несколько прочтений**. Требование
table-driven тестов оказалось единственным местом, где генерации разошлись принципиально, и
произошло это именно потому, что существующий код позволял написать и так, и иначе.

Заметно слабее повлияли **описания архитектуры и направления зависимостей**: модель и без них
не полезла из хендлера в репозиторий напрямую, потому что структура каталогов делает правильный
путь очевидным.

Практически не повлияли **общие формулировки** уровня «пиши идиоматично» и «следуй архитектуре»
из версии v1 — работу за них сделал соседний код, а не сами слова.

## 11. Выводы

На маленьком проекте с внутренне непротиворечивым кодом сильная модель вытягивает стиль почти
без правил, поэтому эффект правил измеряется не тем, стало ли лучше, а тем, стало ли
предсказуемо. Правила убирают элемент везения и фиксируют выбор там, где кодовая база допускает
несколько одинаково разумных решений.

Отсюда следует практический принцип наполнения файла правил: конкретные примеры из самого
проекта важнее абстрактных принципов, а описывать в первую очередь нужно то, что из кода
однозначно не выводится. Дублировать в правилах очевидное — трата контекста впустую.

Наконец, ценность правил растёт вместе с размером и неоднородностью кодовой базы. Там, где
рядом лежит противоречивый легаси-код, приём «прочитать соседний файл» перестаёт работать, и
явно записанная конвенция становится единственным ориентиром — а вместе с ней и раздел о том,
какие места в проекте эталоном считать нельзя.
