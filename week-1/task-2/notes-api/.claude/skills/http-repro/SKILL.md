# Воспроизведение поведения через живой запуск

Юнит-тесты проверяют слои по отдельности и не показывают, что видит клиент.
Симптом, заявленный в терминах HTTP («возвращает 200 вместо 404»), подтверждается
запросом к работающему сервису — иначе легко починить не то.

## Порядок

Запускать из корня репозитория. Сервис слушает порт 8080 и своей команды остановки
не имеет — гасится по имени процесса.

```bash
# 1. поднять в фоне и дождаться готовности
go run ./week-1/task-2/notes-api/cmd/notes-api > /tmp/notes-srv.log 2>&1 &
until curl -s -o /dev/null http://localhost:8080/notes; do sleep 0.4; done

# 2. интересующий запрос — обязательно с кодом ответа
curl -s -w "\nHTTP %{http_code}\n" http://localhost:8080/notes/does-not-exist

# 3. погасить
pkill -f notes-api
```

Тело ответа без кода статуса бесполезно: интересные баги этого сервиса проявляются
именно в расхождении кода и тела.

## Что проверять обязательно

Каждый симптом проверяется **до** правки и **после** неё одной и той же командой,
иначе нет доказательства, что фикс подействовал.

Кроме сломанного сценария всегда проверяй соседний рабочий — чтобы убедиться, что
починка его не задела:

```bash
ID=$(curl -s -X POST -d '{"text":"проверка"}' http://localhost:8080/notes \
     | python3 -c 'import sys,json;print(json.load(sys.stdin)["id"])')
curl -s -w "\nHTTP %{http_code}\n" http://localhost:8080/notes/$ID
```

Один дефект часто виден на нескольких маршрутах: чтение по id, частичное обновление,
удаление. Найдя симптом на одном, проверь остальные, где задействован тот же путь
данных, и выпиши их списком — чинить надо все.

## Если сервис не поднялся

Порт занят прошлым запуском — `pkill -f notes-api` и повторить. Причина в коде —
смотреть `/tmp/notes-srv.log`, там вывод `slog` в JSON.
