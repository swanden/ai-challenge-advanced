# Регрессионный тест, который доказан

Тест, написанный после фикса и сразу зелёный, сам по себе ничего не доказывает: он
может быть зелёным потому, что проверяет не то. Ценность регрессионного теста в том,
что он **падает на старом коде**, и это проверяется фактически, а не рассуждением.

## Порядок

1. Напиши тест на поведение, которое было сломано. Проверяй наблюдаемый результат —
   возвращённую ошибку, код ответа — а не внутреннее устройство реализации.
2. Убедись, что на новом коде он зелёный:
   ```bash
   go test ./week-1/task-2/notes-api/internal/<пакет>/ -run <ИмяТеста> -count=1 -v
   ```
3. **Временно откати фикс** и прогони тест снова — он обязан упасть:
   ```bash
   git stash push -- <файл с фиксом>
   go test ./week-1/task-2/notes-api/internal/<пакет>/ -run <ИмяТеста> -count=1
   git stash pop
   ```
4. Приведи в отчёте оба результата: красный без фикса, зелёный с фиксом. Прошёл на
   старом коде — значит, проверяет не тот путь, переписывай.

Флаг `-count=1` обязателен: без него Go отдаст закешированный результат прошлого
прогона, и «красный» ты не увидишь.

## Где размещать

Тест кладётся в пакет, где лежит причина, а не там, где заметили симптом. Причина в
хранилище — тест в `internal/storage`, даже если проявилось всё в HTTP-слое.

Стиль — как принято в проекте: table-driven, зависимости подменяются дублями, ошибки
сверяются через `errors.Is`. Образец лежит в `internal/note/note_test.go`.

Если в пакете ещё нет файла тестов, создай `<имя>_test.go` рядом с проверяемым кодом
и объяви его в том же пакете, чтобы иметь доступ к неэкспортируемым деталям.

## Чего не делать

Не менять существующие тесты, чтобы новый вписался. Не ослаблять проверку до «функция
что-то вернула». Не заменять регрессионный тест ручной проверкой через curl — она
нужна дополнительно, а не вместо.
